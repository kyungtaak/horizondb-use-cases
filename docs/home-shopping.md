# Home Shopping Intelligence 구성과 검증

작성일: 2026-10-28

HorizonDB Use Cases의 홈쇼핑 사례입니다. 주문 집계와 고객 반응 분석에서 SQL·AI Functions·AI Pipelines의 역할을 살펴봅니다.
앱의 전체 사례 소개에서 **Home Shopping Intelligence**를 선택하거나 상단 **활용 사례** 메뉴로 이동합니다.
공통 이름과 진입 화면을 정리해도 아래의 DB·모델 설정과 기존 검증 기록은 유지하며,
별도 배포나 새로운 모델 통합 검증을 수행했다는 뜻은 아닙니다.

## 구성 설명 발표자료

[Home Shopping Intelligence HTML 발표자료](home-shopping-slides.html)는 생방송 중 고객의 궁금증·구매 망설임을 파악하려는 니즈에서 시작해 현재 데모·처리 구조·추가 AI 활용 아이디어 순서로 설명합니다. 본문 10장·엔딩 1장·참고 5장의 16:9 슬라이드입니다. 시뮬레이터는 참고 1로 옮겼고, 결과 연결·실패 처리는 데이터 모델 참고에, 고정 구간·이동 집계 차이는 마지막 참고에 정리했습니다. 별도의 결과 검증·시간 차트 설명 장은 본문에서 제외했습니다.

현재 저장소에는 PDF 파일이 없습니다. PDF가 필요하면 HTML 발표자료를 열고 브라우저 인쇄에서 저장합니다.
5번 슬라이드에는 단일 HorizonDB와 확장 활용의 역할 분담을 설명합니다.

마지막 본문 장의 이상 주문 징후 탐지, 구매 장벽의 조기 발견, 반복 질문·답변 지원은 현재 미구현인 확장 아이디어입니다. 수치 이상 후보 탐지는 SQL·통계·전용 모델로, 후보의 설명과 확인 항목 제안은 LLM으로 구분합니다. 이 발표자료 수정으로 애플리케이션에 새로운 탐지·답변 기능을 추가한 것은 아닙니다.

2026-10-29의 실제 앱 화면을 포함하고, 성능 수치는 2026-10-28 검증 기록과 구분했습니다. HTML에 이미지·CSS·스크립트가 포함되어 단일 파일로 열 수 있습니다. Fleet와 동일한 네이비 표지·Pretendard·격자 배경·우측 하단 탐색바를 적용했고, 슬라이드 선택·방향키·이미지 확대·브라우저 전체 인쇄(Ctrl+P)를 지원합니다. 한글 폰트는 버전 고정 CDN을 사용하며 오프라인에서는 설치된 폰트로 대체됩니다. 원본 앱 캡처는 `media/home-shopping-overview.png`, `media/home-shopping-timeline.png`, `media/home-shopping-reactions.png`와 댓글·브리핑 확대 이미지 두 개에 보관합니다. 캡처를 위해 기존 실행을 잠시 재개했으며 주문·댓글은 삭제하지 않고 원래의 순항·일시정지 상태로 복원했습니다.

하단 탐색바 수정은 320·390·700·1024·1366·1920px 너비에서 확인했습니다. 개편한 16장의 본문·footer·페이지 번호 잘림, 키보드 이동·이미지 확대, 16페이지 인쇄와 오프라인 폰트 대체를 검사했습니다. 기존 Fleet 발표자료는 수정하지 않았습니다.

## 현재 상태

같은 React 앱의 전체 사례 소개와 헤더 우상단 메뉴에서 `Fleet Intelligence`와 `Home Shopping Intelligence`로 이동합니다. 방문한 사례 화면은 상태를 유지한 채 숨기며, 홈쇼핑의 실행·집계 상태는 백엔드와 DB에서 관리합니다.

홈쇼핑의 데스크톱 헤더에는 `HorizonDB`, `SQL Aggregation`, `AI Pipelines` 기술 배지를 표시합니다. 각 배지의 설명에서 저장·집계·묶음 분석 역할을 확인할 수 있습니다. 모델명은 헤더에 표시하지 않으며, 배지는 개별 서비스의 실시간 정상 상태를 뜻하지 않습니다. AI Pipelines 설명에는 Preview와 외부 모델 추론 경계를 명시했습니다. Fleet 배지와 모바일의 기존 배치는 유지합니다.

기존 검증 환경의 Container App에 백엔드·프론트엔드를 배포해 사례 전환과 Fleet·홈쇼핑 API의 정상 응답을 확인했습니다.
검증 환경의 접속 주소는 공유하지 않습니다. 독자는 공통 실행 안내와 아래 설정을 적용해 자신의 환경에 별도로 설치·배포합니다.

기존 Fleet endpoint의 `gpt-5.4-mini`를 사용해 실제 DB 스키마·모델 등록·댓글 pipeline·브리핑 통합 검증을 수행했습니다. 자동 테스트와 실제 연결 검증의 범위, 성능 목표와 남은 검증은 아래에서 구분합니다.

[요구사항](superpowers/specs/2026-10-28-tv-home-shopping-design.md)과 [구현 계획](superpowers/plans/2026-10-28-home-shopping-v1.md)이 설계 기준입니다.

## 처리 구성

주문·댓글 원문과 AI 작업·분류 결과를 같은 HorizonDB에 보관하고 SQL과 `azure_ai` 확장을 함께 사용합니다. 이 데모는 별도 집계 DB나 외부 ETL·AI 오케스트레이션 서비스를 추가하지 않고, DB의 AI Functions·AI Pipelines로 모델 호출과 원시 결과 저장을 연결한 구성입니다. 다만 외부 처리가 전혀 없다는 뜻은 아닙니다. 백엔드의 수집·묶음 생성·결과 검증은 유지하고, 실제 LLM 추론은 DB에 연결된 외부 모델 endpoint에서 수행합니다.

화면의 시작·일시정지·초기화·상황 변경 요청은 제어 API로 전달합니다. 서버 측 시뮬레이터는 HTTP로 자기 서버를 호출하지 않고 공통 이벤트 처리 함수를 사용해 주문·댓글을 저장합니다.

주문 이벤트 기록과 주문별 상태는 별도 테이블입니다. 주문 이벤트 중복을 제거하고 상태를 재계산하므로 접수·결제·취소 이벤트 수를 주문 건수로 오인하지 않습니다. 취소 차감 전 결제액과 취소·순결제 수치를 구분합니다.

댓글 원문은 `commerce.comments`에 저장합니다. 미처리 댓글이 10건에 도달하거나 가장 먼저 대기한 댓글의 수집 후 5초가 지나면 최대 10건을 `commerce.analysis_batches` 한 행으로 묶습니다. 새 댓글이 들어와도 최초 댓글의 대기 시간을 다시 시작하지 않습니다.

HorizonDB의 `commerce_comment_classifier_v3` `on_change` pipeline은 묶음의 댓글 ID·본문 배열을 하나의 LLM 입력으로 전달하고, `commerce.batch_results.generated_text`에 결과 배열을 저장합니다. 백엔드는 ID 집합이 입력과 정확히 일치하는지, 감정·의도·주제가 유효한지 검사한 뒤 `commerce.labels`에 댓글별로 기록합니다. 근거는 모델이 원문을 다시 생성하게 하지 않고 해당 ID의 원문에 직접 연결합니다. 응답 순서가 바뀌어도 ID로 연결하며, 누락·중복·없는 ID가 포함된 묶음은 실패로 표시합니다. 잘못된 응답을 중립으로 바꾸지 않습니다.

5초는 **수집 대기 조건**입니다. 주기적 확인 스케줄, DB pipeline 대기, 모델 처리와 화면 갱신 시간은 별도입니다. 빈 대기열은 묶음이나 모델 요청을 만들지 않으며 일시정지 후에도 남아 있는 댓글은 시간 조건에 따라 처리합니다. 주문 집계는 이 과정과 독립적입니다.

주문 KPI, 시간대별 주문, 감정 비율, 주제별 고유 댓글 수는 SQL로 계산합니다. 화면은 2초 간격으로 조회합니다. 비율 분모에는 긍정·중립·부정으로 판정한 댓글만 포함하고 판정 불가·대기·실패를 별도 표시합니다.

브리핑은 주문 생성과 분리해 30초 주기로 요청합니다. 모델에는 집계와 댓글 근거를 전달하며, 모델이 화면 지표를 직접 계산하지 않습니다. 생성 시각과 데이터 기준 시각을 구분합니다. 모델 호출 실패는 실패 상태로 보존합니다.

한 실행은 방송 B-001과 상품 P-1042에 대응합니다. 별도의 다중 방송·상품 필터는 없습니다. 예시 상품 가격은 99,000원, 수량은 한 주문에 한 개, 결제액 목표는 2억 원입니다.

## 설정과 실행

### 모델 선택

Fleet와 홈쇼핑의 모델 alias는 독립적입니다. 첫 버전은 이미 배포된 `gpt-5.4-mini`를 명시적으로 지정해 사용하는 구성을 권합니다. 코드의 classifier 기본 deployment는 `gpt-5.4-nano`이므로 아래 설정을 적용해야 합니다. nano에서 mini나 기존 대형 모델로 자동 대체하지 않습니다.

```dotenv
COMMERCE_ENABLED=true
COMMERCE_CLASSIFIER_ALIAS=horizonshop-classifier
COMMERCE_CLASSIFIER_DEPLOYMENT=gpt-5.4-mini
COMMERCE_BRIEFING_ALIAS=horizonshop-briefing
COMMERCE_BRIEFING_DEPLOYMENT=gpt-5.4-mini
```

현재 DB의 `azure_ai` 2.5.3에서는 BYOM 모델 등록 시 Managed Identity를 지원하지 않는다는 실제 오류를 확인했습니다. 이 경로에는 subscription-key가 필요합니다. 구독 정책으로 key 인증을 비활성화한 별도 모델 계정의 정책이나 설정을 변경하지 않습니다.

사용자가 기존 Fleet endpoint에 `gpt-5.4-mini`를 추가했습니다. 해당 endpoint와 기존 key를 재사용해 홈쇼핑 전용 alias 두 개를 등록했습니다. 실제 응답 모델은 `gpt-5.4-mini-2026-03-17`입니다. endpoint·key를 브라우저나 이미지에 넣지 않았습니다.

다른 endpoint를 쓰는 환경을 위한 설정 항목은 다음과 같습니다.

```dotenv
COMMERCE_MODEL_ENDPOINT=https://your-model-account.openai.azure.com/
COMMERCE_MODEL_AUTH_TYPE=subscription-key
```

현재 인스턴스에서 `COMMERCE_MODEL_AUTH_TYPE=managed-identity`로 BYOM을 등록하면 실패합니다. 역할이 부여되어 있어도 지원되는 인증 방식이라는 뜻은 아닙니다. 이 기능은 identity, RBAC, 모델 계정의 `disableLocalAuth`를 자동 변경하지 않습니다.

별도 설정이 없으면 기존 `AZURE_OPENAI_ENDPOINT`, `MODEL_REGISTRY_AUTH_TYPE`, `AZURE_OPENAI_KEY`를 사용합니다. 다른 계정에 subscription key로 연결한다면 `COMMERCE_MODEL_KEY`도 별도로 지정합니다. key를 프론트엔드나 저장소에 넣지 않습니다.

### 명시적인 DB 설정

DB에 접근할 수 있는 환경에서 저장소 루트 기준으로 실행합니다. 기존 배송 테이블과 pipeline은 변경하지 않습니다.

```powershell
Set-Location backend
.\.venv\Scripts\python.exe -m app.commerce.setup
```

추가 환경 파일을 선택할 수도 있습니다. 프로세스 환경 변수는 파일보다 우선합니다.

```powershell
.\.venv\Scripts\python.exe -m app.commerce.setup --env-file ..\.azure\krc\.env
```

설정 명령은 스키마, 두 모델 alias, 분류 pipeline을 구성하고 실제 classifier 호출을 검사합니다. 모델 연결에 실패하면 오류를 반환합니다. 이미 존재하는 alias의 endpoint·deployment·인증 방식이나 pipeline 정의가 다르면 임의로 덮어쓰지 않습니다.

처음 시작하기 전에 설정합니다. 이미 시뮬레이터가 실행 중이면 일시정지하고 대기 중인 pipeline 처리가 끝난 뒤 점검 시간에 실행합니다. 실행 중인 데모가 있으면 설정 명령이 명시적으로 중단됩니다. DDL은 모델 연결 검사 전에 별도 commit하므로, 모델 검사 실패 시에도 생성한 테이블은 남을 수 있습니다. 이 명령은 무중단 온라인 migration 도구가 아닙니다.

v1에서 전환할 때는 기존 댓글·원문 분석 결과·label을 보존하고, 댓글당 pipeline의 정의와 trigger만 `ai.drop_pipeline`으로 제거합니다. 실제 인스턴스에서는 v1을 단순히 pause하면 INSERT trigger가 오류를 발생시켜 댓글 저장을 막았기 때문입니다. 묶음 pipeline은 새 테이블·이름으로 구성하며, 기존 성공 label을 다시 분석하지 않습니다.

현재 개발 PC에서는 한국 리전 DB의 직접 접속이 timeout되어, 기존 VNet 연결 백엔드 컨테이너에서 설정·검증했습니다. `azure_ai` 2.5.3의 pipeline 생성과 `on_change` 실행·sink 저장을 실제로 확인했습니다. 별도 `pg_durable` 확장 설치를 새로 수행하지 않았습니다.

그다음 기존 방식으로 백엔드와 프론트엔드를 실행합니다.

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:create_app --factory --host 127.0.0.1 --port 8000
```

```powershell
Set-Location frontend
npm run dev
```

`COMMERCE_ENABLED=false`이면 홈쇼핑 API는 명시적으로 503을 반환하고 Fleet는 계속 동작합니다. true여도 홈쇼핑 초기화가 실패하면 서버 로그와 화면 오류에서 원인을 확인할 수 있으며, Fleet 초기화 경로와 분리됩니다.

### 데모 진행

1. 헤더에서 홈쇼핑을 선택합니다. 기존 실행을 처음 장면부터 비교하려면 `01 판매 순항`을 선택한 뒤 제품 옆 `시작`을 누릅니다.
2. 판매 순항 장면에서 주문·댓글 유입과 분석 대기·완료 상태를 확인합니다.
3. 같은 상단 영역의 `02 배송 문의 급증`을 누르고 이후 댓글·주문 흐름을 관찰합니다.
4. `03 안내 보강·회복`을 누릅니다. 별도 입력 없이 기본 안내 문구를 기록하고 회복 장면으로 전환합니다. 버튼 아래에는 “배송·출고 안내 후 고객 반응 회복” 설명만 표시합니다.
5. 시간 추이의 대응 기록과 이후 고객 반응을 비교합니다.
6. 태그를 선택해 같은 조회 구간의 근거 댓글을 확인합니다.

상황 버튼은 이후 생성할 이벤트만 바꿉니다. 기존 주문 수나 감정 라벨을 목표 수치로 덮어쓰지 않습니다. 시뮬레이션의 상관관계는 시연을 위해 구성한 것이며 실제 고객 행동의 인과적 증거가 아닙니다.

순항·문의 급증·회복 장면의 주문 발생 확률은 각각 약 40·20·45건/분에 대응합니다. 댓글은 약 30건/분으로 생성합니다. 실제 속도는 DB 처리 지연에 따라 달라질 수 있습니다. 아직 처리량 성능을 보증하는 측정값은 없습니다.

일시정지는 신규 이벤트만 멈춥니다. 기존 댓글 분석은 계속될 수 있습니다. 초기화는 확인 후 새 실행 ID를 만들며 과거 데이터는 보존합니다. 도메인 전환은 초기화나 정지를 수행하지 않습니다.

## 검증 방법과 관찰 결과

### 자동 검사

백엔드 작업 디렉터리에서 실행합니다.

```powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m ruff check app\commerce tests\test_commerce.py tests\test_commerce_api.py tests\test_commerce_batching.py tests\commerce_browser_fixture.py
```

프론트엔드는 기존 `npm run build`, `npm run lint`를 사용합니다.

브라우저 fixture 서버는 테스트 전용입니다. 실제 모델을 사용하는 데모나 운영 fallback이 아닙니다.

```powershell
# backend 디렉터리, 테스트할 때만 사용
.\.venv\Scripts\python.exe -m uvicorn commerce_browser_fixture:app --app-dir tests --host 127.0.0.1 --port 8000
```

이 fixture로 도메인 전환 후 Fleet 검색 입력 유지, 시작·상황 주입·대응 기록, 주제 선택, 390px 화면의 도메인 선택기 노출, API 503 발생 시 이전 값의 기준 시각 표시를 확인했습니다.

실제 DB 연결 환경의 별도 통합 검사는 다음 명령입니다. 활성 데모가 있으면 다른 실행을 덮어쓰지 않고 중단합니다. 합성 데이터만 사용하지만 실제 모델 비용이 발생합니다.

```powershell
.\.venv\Scripts\python.exe -m app.commerce.check
```

검사는 중복 결제, 취소 이벤트 순서 역전, SQL 합계·분 단위 bucket, 초기화 격리, 실제 pipeline 20개 댓글, 실제 브리핑을 확인합니다. classifier p95를 측정하지만 브라우저 화면 반영 지연까지 측정하는 검사는 아닙니다.

현재 검사는 20건이 두 개의 10건 묶음으로 들어가는지, 부분 묶음은 5초 전에 생성되지 않고 시간이 지나면 생성되는지, 동시 flush 요청이 한 작업만 만드는지도 검사합니다. 기존 일시정지 데모를 보존하면서 검사하려면 `--isolate-paused-run`을 명시합니다. 검사 중 공개 조작을 피해야 하며, 원래 실행은 삭제하지 않고 검사 종료 시 복원합니다.

### 실제 연결 검증 결과

기존 Fleet endpoint의 mini 모델에 직접 요청해 `MINI_OK` 응답을 확인했습니다. DB 모델 등록 후에는 HorizonDB AI pipeline으로 합성 댓글 20건을 실제 분류했습니다. 20건 모두 분석 완료되었고, 이 실행에서 긍정 8건·중립 8건·부정 4건, 실패 0건이었습니다. 이 분포는 해당 실행 결과이지 고정된 정답이나 품질 보증 수치가 아닙니다.

실제 SQL로 중복 결제, 취소 이벤트 순서 역전, 결제액·채널 합계·분 단위 bucket, 초기화 후 실행 격리를 확인했습니다. 재시도 결과보다 이전 결과가 늦게 도착해도 sink의 source version이 역행하지 않는지 검사했습니다. 실제 mini 브리핑도 완료되었고 입력에 있는 댓글 ID만 근거로 참조했습니다.

이하의 지연 수치는 **댓글당 호출을 사용한 최초 v1 검증값**입니다. micro-batch의 성능 측정값으로 해석하면 안 됩니다. v1에서 20건을 한꺼번에 입력한 burst 검사의 수집부터 분석 저장까지 p95는 **27.40초**였습니다. 이 검사는 정상 속도로 계속 유입하는 시나리오와 다릅니다.

v1의 연속 유입 댓글 20건에서는 수집부터 분석 저장까지 p95 **3.55초**, 최대 **4.07초**를 측정했습니다. 이 구간의 실제 댓글 간격은 평균 약 2.29초였습니다. 화면의 2초 polling까지 포함한 지연 목표와 DB 저장 지연을 동일시하지 않습니다.

브라우저 DOM 반영 지연도 관찰했지만, 통합 브라우저의 `document.visibilityState`가 `hidden`인 상태에서는 timer가 제한되어 일관된 측정 조건을 만들지 못했습니다. 화면의 주문 5초·댓글 p95 15초 목표는 foreground 브라우저에서 정밀 재측정해야 하며, 이번 DB 측정으로 완전 충족을 선언하지 않습니다.

실제 출력에서 근거 문장 전체에 인용부호를 덧붙이는 사례를 발견했습니다. 원문과 일치하는 인용부호 안쪽 문자열만 정규화하도록 수정했고, 원문에 없는 문장은 여전히 실패로 처리합니다. 이 사례의 회귀 테스트를 포함해 백엔드 **166개 테스트**가 통과했습니다.

### Micro-batch와 UI 후속 변경

후속 단위 테스트에는 4.999초·정확히 5초·10건 도달·빈 대기열과 응답 ID 누락·중복·재정렬 검사를 추가했습니다. 생성기의 run row lock은 batch insert의 외래 키 검사와 충돌하지 않는 `FOR NO KEY UPDATE`를 사용합니다. 재시도는 새 source version과 새 batch assignment를 만들고, 늦게 도착한 이전 결과는 현재 label에 덮어쓰지 않습니다.

첫 묶음 모델 검증에서는 모델이 인용부호를 중첩해 JSON을 잘못 생성한 사례를 확인했습니다. 파서를 느슨하게 고쳐 잘못된 출력을 성공 처리하는 대신, 모델 응답을 댓글 ID와 고정된 분류 값으로 줄였습니다. 원문 근거는 서버에서 해당 ID로 연결하므로 이스케이프 오류 위험과 응답 토큰을 줄이고 원문을 보존합니다. 초기 묶음 pipeline v2는 이 응답 규격으로 교체한 v3에 통합합니다.

최종 v3를 기존 Azure 데모에 배포하고 다음 결과를 확인했습니다.

| 검증 항목 | 실제 결과 |
| --- | --- |
| 20건 burst | 10건·10건의 작업 두 개로 분류. 각 모델 입력의 `comments` 배열 길이 10 |

여기서 작업 두 개는 논리적인 분류 요청 수입니다. 모델 재시도나 설정용 smoke test, 운영 브리핑까지 포함한 HTTP 요청 수·전체 청구 금액을 뜻하지 않습니다. 평상시 유입에서는 5초 동안 모인 1~몇 건을 처리하므로 모든 요청이 열 건으로 채워지지는 않습니다.

최종 백엔드 **186개 테스트**, 프론트엔드 빌드·린트가 통과했습니다. 실제 모델을 사용한 검사와 공개 앱 정상 동작을 확인한 후 시뮬레이터를 다시 일시정지했습니다. 최초 댓글당 v1의 지연 수치와 최신 묶음 결과를 혼용하지 않습니다.

관심 주제는 테두리·옅은 배경·건수 배지로 구분하며 선택 상태에는 추가 테두리를 표시합니다. 데스크톱 1024px·1440px에서 제품명을 한 줄로 표시하도록 헤더의 브랜드 영역을 넓혔습니다. 390px 모바일의 기존 두 줄 배치와 선택기 위치는 유지합니다.

실제 공개 앱에서 정상 → 배송 문의 → 안내 보강 장면, 대응 시각 기록, 주문·감정·브리핑 표시, 도메인 왕복 전환을 확인했습니다. 같은 시작 요청을 반복해도 실행 ID가 유지되었고, 별도 DB 연결의 생성기 lock 획득이 거절되었습니다. 재배포 후에는 기존 실행이 정지 상태로 인계되는 것도 확인했습니다.

실패한 조회 조건이 이전 데이터를 잘못 표시하던 리뷰 지적은 수정했습니다. 명시적인 로컬 fixture의 API 실패로 검증했으며, 최근 5분·배송을 요청했어도 성공한 결과가 최근 1분·전체 주제라면 이전 조건을 그대로 표시하고 미적용 상태를 알립니다.

별도 모델 계정의 `disableLocalAuth=true`와 구독 정책은 변경하지 않았습니다. Managed Identity 미지원으로 중단된 첫 설정 트랜잭션은 롤백되었으며, 현재는 기존 endpoint의 subscription-key 경로만 사용합니다. 초기 콘솔 요청 제한 때의 부분 전송 임시 파일도 정리했습니다.

검증을 마친 공유 시뮬레이터는 비용이 계속 발생하지 않도록 일시정지했습니다. 확인한 주문·분류·대응 기록은 보존합니다. 화면에서 시작하면 같은 실행을 재개하고, 초기화하면 새 실행을 준비합니다.

## 시나리오 UI와 시간 차트 후속 개선

실행 제어는 제품 제목 옆의 시작·일시정지·초기화로 유지하고, 세 장면은 상단의 한 영역에 모았습니다. 시작은 현재 장면을 재개하므로 회복 상태에서 다시 시작해도 자동으로 순항 장면이 되지는 않습니다. 장면 선택과 실행 제어의 역할을 화면에 명시했습니다.

2026-10-29에는 별도 방송 안내 입력칸을 제거하고 03 버튼 아래의 짧은 설명으로 대체했습니다. 버튼을 누르면 기존 기본 문구인 “결제 후 영업일 기준 2일 이내 출고, 도착일은 지역별로 다름”을 기록합니다. 대응 시각 기록·회복 장면 전환·차트 표시 동작은 유지합니다.

새 UI의 기본 차트는 최근 5분을 10초 단위로 표시하며, 최근 15분·1분 단위 보기로 전환할 수 있습니다. 두 차트는 같은 시간축을 사용하고 y축에 건수·% 눈금을 표시합니다. 단일 값이나 0% 값도 점으로 그립니다. 마지막 구간은 아직 집계 중임을 표시합니다.

부정 비율의 분모는 해당 고정 구간에서 긍정·중립·부정으로 판정된 댓글 수입니다. 댓글 없음, 판정 가능한 분석이 아직 없는 대기 구간, 판정 불가·실패만 있는 구간은 0%로 채우지 않습니다. 일부 분석이 대기 중이면 완료된 댓글로만 비율을 계산하고 tooltip에 대기·실패 건수를 표시합니다.

오른쪽 고객 분위기는 직전 60초 또는 300초의 **이동 집계**이고, 차트는 시간 경계로 나눈 **고정 구간 집계**입니다. 따라서 오른쪽 비율과 차트의 마지막 점이 항상 같아야 하는 것은 아닙니다. 상단 직전 60초 주문 지표도 같은 이유로 차트의 현재 구간 주문과 구분합니다.

새로운 순항·배송 장면 전환과 안내 보강은 실제 시각과 장면 종류를 DB에 기록합니다. 두 차트에 같은 시각의 전환선을 표시하며, 선택 구간 밖의 과거 안내는 목록과 차트에서 제외합니다. 이전에 기록하지 않은 순항·배송 시각을 추정해 채우지는 않습니다. 같은 장면을 다시 선택하는 것으로 중복 전환 기록을 만들지 않습니다.

API는 `timeline_seconds=300&bucket_seconds=10` 또는 `timeline_seconds=900&bucket_seconds=60`을 받습니다. 기존 호출을 위해 API 자체의 기본값은 900/60으로 유지하고, 새 UI가 300/10을 명시적으로 요청합니다. 기존 `minute` 필드는 호환성을 위해 유지하지만 이제 선택한 고정 구간의 시작 시각을 뜻하며 10초 보기에서는 초 단위를 포함합니다.

### 검증 결과

- 백엔드 196개 테스트, 네이티브 Node 차트 계산 테스트 4개, 프론트엔드 빌드·린트 통과.
- 브라우저 fixture에서 상단 3단계 동작, 단일 0% 점, 댓글 없는 차트, 대기만 있는 차트, 혼합 상태와 두 조회 모드 전환 확인.
- 390px·1024px·1440px에서 가로 페이지 overflow 없음 확인.
- 실제 DB의 정확한 경계 입력을 검사해 10초 구간별 `[2, 2, 1]`건을 확인. 같은 이벤트를 두 구간에 넣지 않음.
- 실제 3단계 시연에서 기존 주문 269건을 유지한 채 20건이 추가되었고, 댓글 17건 분석 완료·실패 0건을 확인.
- 실제 장면 시각은 21:06:08 순항, 21:06:21 배송 문의, 21:06:33 안내 보강으로 저장됨. 해당 실행의 10초 부정 비율은 배송 구간 80%, 전환이 섞인 다음 구간 40%, 이후 구간 0%로 관찰됨. 이는 시연 결과이며 고정된 모델 정답이나 인과 효과 보장이 아님.
- 5분/10초와 15분/60초의 실제 차트 합계를 원본 주문·댓글과 대조해 각각 주문 20건·댓글 17건·구간 내 장면 기록 3건이 일치함을 확인.

읽기 전용 재검사는 백엔드 환경에서 `python -m app.commerce.check --timeline-only`로 실행합니다. 차트 계산 테스트는 프론트엔드에서 `npm run test:commerce`로 실행합니다.

검증 후 공유 시뮬레이터는 다시 일시정지했습니다. 실시간 창은 정지 중에도 현재 시각을 기준으로 이동하므로 시간이 지나면 이전 점·전환 기록이 창 밖으로 빠집니다. 15분 보기로 범위를 넓히거나 시뮬레이터를 재개해 새 구간의 변화를 관찰할 수 있습니다.

## 추가 작업

현재 공개 데모는 실제 mini 모델과 연결되어 있습니다. 다량 댓글이 한 번에 들어오는 상황의 지연 개선, 한국어 분류 품질 평가, 프로세스 장애·인계와 실제 모델 timeout·할당량 오류 주입 검증이 추가 작업입니다. 단위·fixture 검증을 실제 외부 서비스 장애 검증으로 소개하지 않습니다.

현재 배포는 기존 Container Apps 설정을 명시적으로 갱신한 결과입니다. `azd up` 재배포에서도 홈쇼핑 설정과 schema setup을 재현하려면 인프라 템플릿·배포 hook에 별도 연결하는 작업이 필요합니다.

운영 확장에는 사용자 권한·제어 API 보호, 여러 방송·상품, 실제 주문 수신 API, 부분 취소·환불, 고객 개인정보 처리와 별도 부하 검증이 필요합니다. 현재 공개 서비스 운영용 권한 체계를 구현했다고 주장하지 않습니다.
