# TV 홈쇼핑 실시간 운영 대시보드 요구사항

작성일: 2026-10-28

상태: 2026-10-28 사용자 승인 후 첫 버전 구현. 실제 충족·검증 상태는 [구성·검증 보고](../../home-shopping.md)를 따릅니다.

## 1. 목적과 사용 장면

TV 홈쇼핑 책임자가 생방송 중 상품의 판매 흐름과 고객 분위기를 한 화면에서 확인합니다. 주문이 얼마나 들어오는지뿐 아니라 고객이 무엇을 궁금해하고 어디서 구매를 망설이는지 파악하고, 진행자에게 설명 보강을 제안하는 데모입니다.

데모의 이야기는 **판매 순항 → 배송 문의 급증 → 안내 보강 이후 변화 확인**으로 구성합니다. 판매와 고객 반응을 같은 시간축에서 관찰하되, 두 지표의 동시 변화만으로 인과관계를 단정하지 않습니다.

### 사용자와 합의한 사항

| 항목 | 합의 내용 |
| --- | --- |
| 용도 | 실제 고객 운영 시스템이 아닌 시연용 데모 |
| 주 사용자 | 생방송을 진행하면서 판매와 고객 분위기를 확인하는 TV 홈쇼핑 책임자 |
| 기존 기능 | Fleet Intelligence 유지 |
| 도메인 전환 | 헤더 우상단 콤보박스에서 Fleet와 홈쇼핑 화면 전환 |
| 데이터 | 주문과 댓글은 재현 가능한 가상 이벤트로 생성 |
| AI | 댓글 분석과 운영 브리핑은 실제 LLM으로 수행 |
| 시나리오 | 판매 순항, 배송 문의 급증, 안내 보강 이후 변화 확인 |

이하의 지표 정의, 초기값, 세부 동작은 작성자가 제안한 설계입니다. 문서 승인으로 첫 버전의 기준을 확정하며, 이미 구현되거나 성능이 검증된 사항을 뜻하지 않습니다.

## 2. 범위와 제외 사항

첫 버전은 한 방송과 한 상품에 집중합니다. 예시 상품은 99,000원짜리 에어프라이어이며, 모든 주문은 수량 1개·할인 없음·전액 결제 조건으로 생성합니다. 여러 SKU, 부분 취소, 부분 환불은 다루지 않습니다.

필수 범위는 도메인 전환, 주문 집계, 실제 LLM 댓글 분류, 태그별 원문 확인, 운영 브리핑, 방송 대응 시점 기록, 데모 조작과 처리 상태 표시입니다.

다음 항목은 첫 버전에서 제외합니다.

- 실제 홈쇼핑 주문·결제·댓글 플랫폼 연결
- 실제 재고, 배송 추적, 고객 개인정보 처리
- 시청자 수를 분모로 쓰는 구매 전환율
- 매출 예측, 대응 효과의 인과 추정, 자동 가격 조정
- 자동 방송 제어, 고객에게 자동 댓글 답변 발송
- 여러 방송 동시 운영, 사용자별 독립 데모, 운영용 권한 체계
- 홈쇼핑 댓글의 벡터 검색과 신규 Azure 리소스 배포

기존 Fleet의 검색, 지도, AI 도우미와 관련 데이터·설정은 유지합니다.

## 3. 도메인 선택과 화면 구성

### 헤더 콤보박스

두 선택지는 `Fleet Intelligence`와 `Home Shopping Intelligence`로 제안합니다. 홈쇼핑 영문 이름은 작성자의 제안입니다.

최초 접속은 기존 Fleet 화면을 기본으로 유지합니다. 콤보박스는 선택한 도메인의 화면과 도메인별 탐색 메뉴를 바꿉니다. 기존 Fleet의 헤더 내 제품명과 도메인 선택이 중복되지 않도록 통합하되, 선택기는 우상단에 배치합니다.

도메인 선택 자체는 데모의 시작·정지·초기화를 수행하지 않습니다. 홈쇼핑 화면을 떠났다가 돌아와도 같은 실행의 최신 상태가 표시되어야 합니다. Fleet의 검색 조건과 홈쇼핑의 조회 구간도 서로 섞이지 않아야 합니다.

페이지 새로고침 후 선택 도메인을 기억하는 방식과 URL 구조는 구현자가 기존 앱 패턴에 맞춰 정합니다. 첫 버전의 데모 실행은 서버가 관리하는 단일 공유 실행이며, 화면을 숨겼다고 이벤트 생성이 중단되는 구조는 피합니다.

### 홈쇼핑 화면

| 영역 | 표시 내용 | 책임자가 확인하는 질문 |
| --- | --- | --- |
| 방송·상품 | 방송 시간, 상품명, 가격, 실행 상태 | 지금 어떤 상품을 판매하는가 |
| 판매 KPI | 결제 완료 주문, 결제액, 목표 달성률, 최근 1분 주문, 취소 | 잘 팔리고 있는가 |
| 시간 추이 | 분당 주문과 부정 반응, 대응 시점 | 언제 흐름이 바뀌었는가 |
| 고객 분위기 | 감정 비율, 분석 상태, 태그 클라우드 | 무엇을 느끼고 궁금해하는가 |
| 댓글 근거 | 원문, 감정, 발화 의도, 주제 | 판정의 근거가 무엇인가 |
| 운영 브리핑 | 상황 요약, 근거, 설명 보강 제안 | 지금 어떤 내용을 설명할 것인가 |
| 주문 이벤트 | 최근 주문의 시각·채널·상태 | 실제 이벤트가 계속 들어오는가 |
| 데모 조작 | 시작, 일시정지, 초기화, 상황 주입, 대응 기록 | 어떤 장면을 시연할 것인가 |

데스크톱 화면에서 KPI와 주요 추이를 먼저 읽을 수 있게 구성합니다. 화면이 좁으면 세로로 배치하며, 모든 영역을 한 화면에 억지로 축소하지 않습니다. 서비스 구현은 기존 앱의 디자인·접근성·폰트 규칙을 따릅니다. 별도 HTML 목업의 색상과 폰트는 구현 규격이 아닙니다.

## 4. 데모 시나리오와 조작

### 세 가지 장면

| 장면 | 생성할 이벤트의 성격 | 화면에서 확인할 변화 | 진행 판단 |
| --- | --- | --- | --- |
| 판매 순항 | 꾸준한 결제, 용량·세척 질문, 긍정적 감상 | 주문 추이와 관심 주제 | 가족 기준 조리량 설명 |
| 배송 문의 급증 | 배송 일정 질문·불만 증가, 주문 유입 속도 감소 | 배송 태그 증가, 부정 반응과 주문 흐름 | 확인된 출고 일정 안내 |
| 설명 보강 이후 | 배송 불안 문구 감소, 감사·구매 언급 증가, 주문 속도 회복 | 대응 시점 이후의 추이 | 안내 유지, 남은 질문 확인 |

장면은 이벤트 생성 규칙을 바꿉니다. 버튼을 눌렀다고 기존 집계나 LLM 판정을 목표 수치로 덮어쓰지 않습니다. 시연의 재현성은 이벤트 종류·순서·발생 시각에 적용하며, 실제 LLM의 문구와 분류 결과가 매번 완전히 같을 것이라고 보장하지 않습니다.

초기 화면이 비어 있지 않도록 가상 방송의 과거 주문을 준비할 수 있습니다. 과거 댓글도 표시한다면 실제 LLM으로 분석한 결과만 사용하며, 분석되지 않은 댓글은 대기 상태로 표시합니다. 장면별 기대 감정 라벨은 검증용 fixture에만 두고 모델 입력의 정답으로 전달하지 않습니다.

### 조작 규칙

- 시작은 새 실행을 만들거나 일시정지한 실행을 재개합니다. 이미 실행 중이면 중복 생성기를 시작하지 않습니다.
- 일시정지는 새 이벤트 생성을 멈춥니다. 이미 수집한 댓글의 분석과 결과 반영은 계속 허용합니다.
- 상황 주입은 이후 이벤트의 분포와 문구를 바꿉니다. 버튼의 역할은 방송을 실제로 제어하는 것이 아닙니다.
- 안내 보강은 책임자가 대응 내용을 기록한 뒤 회복 장면을 시작합니다. 대응 시각과 문구를 시간 추이에 표시합니다.
- 초기화는 확인 후 새 `run_id`를 만듭니다. 새 실행의 집계에는 이전 실행의 데이터나 늦게 도착한 LLM 결과를 포함하지 않습니다.

첫 버전은 실시간 시계로 진행하며 배속 재생은 제외합니다. 짧은 시연을 위해 고객 반응은 최근 1분을 기본으로, 최근 5분도 선택할 수 있게 제안합니다. 초기 HTML 목업은 최근 5분만 표시하지만 최종 화면의 구간 선택 요구사항을 대체하지 않습니다.

초기 이벤트 속도는 순항 시 주문 약 40건/분·댓글 약 30건/분을 제안합니다. 문의 급증 장면에서는 주문을 약 20건/분으로 낮추고 배송 관련 댓글 비중을 높입니다. 회복 장면은 주문 약 45건/분을 사용합니다. 이는 부하 성능 목표가 아니라 작성자가 제안한 시연 데이터 분포입니다.

## 5. 판매 지표와 집계 규칙

모든 지표는 현재 `run_id`, 방송, 상품으로 범위를 제한합니다. 누적 지표는 해당 방송 시작부터, 구간 지표는 화면이 요청한 기준 시각의 `[시작, 끝)` 구간으로 계산합니다. 서로 다른 카드에 같은 기준 시각을 적용하고 마지막 갱신 시각을 표시합니다. 저장 시각은 UTC를 사용하고 화면은 한국 시각으로 표시합니다.

첫 버전의 주문 상태는 `접수 → 결제 완료 → 결제 취소`입니다. 취소는 결제 완료 주문의 전액 취소만 생성합니다.

| 지표 | 정의 |
| --- | --- |
| 접수 주문 수 | 중복을 제거한 접수 주문 수. 결제 완료 수와 구분 |
| 누적 결제 완료 주문 | 한 번 이상 결제 완료된 주문의 고유 건수. 이후 취소되어도 이 수치는 유지 |
| 누적 결제액 | 결제 완료 시 확정된 금액의 합계. 취소 차감 전임을 명시 |
| 취소 주문·금액 | 결제 후 취소된 고유 주문 수와 해당 금액 |
| 순결제 주문·금액 | 누적 결제 완료에서 취소를 차감한 수치 |
| 목표 달성률 | 취소 차감 전 누적 결제액 / 방송 결제액 목표. 카드에 기준 명시 |
| 최근 1분 주문 | 최근 60초에 결제 완료된 고유 주문 수 |
| 채널별 주문 | TV 전화·앱·웹의 결제 완료 주문 수 |

기본 KPI는 누적 결제 완료 주문, 취소 차감 전 결제액, 같은 기준의 목표 달성률, 최근 1분 결제 완료 주문입니다. 취소와 순결제 수치는 보조 영역에 함께 표시합니다. 제안 목표액은 2억 원입니다.

집계는 DB의 주문 이벤트·상태에서 계산하고 LLM에 산술 계산을 맡기지 않습니다. “구매했어요”라는 댓글은 구매 언급으로만 분류하며 주문 집계에 더하지 않습니다.

`event_id`는 중복 수신을 제거하고 `order_id`는 같은 주문의 상태 전이를 연결합니다. 중복 결제 이벤트로 주문·금액을 두 번 더하면 안 됩니다. 취소 이벤트가 결제 완료보다 먼저 수신되는 순서 역전도 결과 집계가 일관되도록 처리합니다. 같은 상품·주문의 최신 상태와 최초 결제 사실을 구분해 보관합니다.

## 6. 댓글 분석과 태그 클라우드

### 분석 결과

댓글 한 건의 감정, 의도, 주제를 별개 필드로 보관합니다.

| 차원 | 첫 버전의 값 |
| --- | --- |
| 감정 | 긍정, 중립, 부정, 판정 불가 |
| 발화 의도 | 질문, 불만, 감상, 구매 의향, 구매 언급, 기타. 복수 선택 허용 |
| 주제 | 배송, 출고일, 가격·혜택, 용량, 조리 결과, 세척, 구성품, 기타. 복수 선택 허용 |
| 근거 | 판정의 근거가 되는 원문 구절 또는 짧은 설명 |
| 처리 정보 | 처리 상태, 처리 시각, 사용 모델·분류 규칙 버전 |

고정 주제 목록으로 표현을 정규화합니다. 예를 들어 “언제 와요”와 “배송일”을 무조건 별도 단어로 세지 않고 댓글 문맥에서 배송 주제로 판정합니다. 고정 목록으로 분류하기 어려운 내용은 명시적으로 기타로 분류하며 원문을 유지합니다.

“배송이 언제인지 안내가 없어서 답답해요. 금요일까지 오나요?”는 `부정 / 질문·불만 / 배송`이 될 수 있습니다. 질문이라는 이유로 중립으로 고정하지 않습니다. 반어·문맥 부족 등으로 감정을 결정하기 어려우면 판정 불가를 허용하며, 모델의 자체 확신도를 정확도로 표현하지 않습니다.

모델 출력은 구조화된 형식으로 검증합니다. 필드 누락, 잘못된 enum, 원문에 없는 댓글 ID와 파싱 오류는 분석 실패로 처리합니다. 실패를 중립 판정이나 가짜 분석 결과로 바꾸지 않습니다.

### 집계와 원문 확인

선택 구간의 고유 댓글을 기준으로 집계합니다. 감정 분포의 분모는 분석이 완료되고 긍정·중립·부정으로 판정된 댓글 수입니다. 판정 불가, 대기, 처리 중, 실패는 각각 별도 수치로 표시합니다. 분모가 0이면 0% 대신 분석 결과 없음으로 표시합니다.

태그 크기와 숫자는 해당 주제를 한 번 이상 언급한 고유 댓글 수를 반영합니다. 댓글 하나의 같은 주제는 한 번만 세며, 복수 주제 때문에 태그 건수의 합은 댓글 수보다 클 수 있습니다.

태그를 선택하면 같은 방송·상품·조회 구간의 근거 댓글 목록이 표시됩니다. 감정·의도·원문을 함께 읽을 수 있어야 합니다. 댓글 ID와 생성 시각을 보존하고, 목록 표시 개수와 페이지 처리 방식은 구현자가 정합니다.

### 경고의 초기 기준

알림 기준은 작성자의 제안이며 UI와 테스트에 같은 값을 적용합니다. 최근 1분에 감정 판정이 가능한 댓글이 20건 이상이고, 부정 비율이 40% 이상이며, 분석 완료 댓글 중 배송 주제가 10건 이상이면 배송 반응 경고를 표시합니다. 같은 조건이 유지되는 동안 같은 경고를 매 갱신마다 쌓지 않습니다.

댓글 수가 적거나 분석이 밀리면 충분한 분석 결과가 없다는 상태를 표시합니다. 주문 감소는 별도 관찰 지표이며 배송 반응 경고의 필수 조건은 아닙니다. 경고 조건은 실제 분석 결과로 판단하므로 상황 주입이 경고 발생을 강제로 보장하지 않습니다.

## 7. 운영 브리핑과 대응 기록

브리핑은 LLM이 현재 집계, 최근 관심 주제, 대표 댓글, 기록된 대응 내용을 받아 작성합니다. 결과에는 상황 요약, 근거 지표·댓글 ID, 책임자가 검토할 진행 제안을 포함합니다.

모델이 임의의 주문 수·비율·배송 약속을 생성하면 안 됩니다. 지표는 서버가 계산한 값을 사용하고 화면에서도 해당 값을 직접 표시합니다. 출고 일정처럼 운영 사실이 필요한 제안에는 데모용 상품 안내 정보를 함께 전달합니다. 이 정보도 가상임을 명시합니다. 근거가 없는 도착일은 제시하지 않습니다.

기본 갱신 주기는 30초로 제안합니다. 경고 상태가 바뀌거나 책임자가 수동 갱신하면 추가 갱신하되, 같은 실행의 중복 요청을 제한합니다. 매 댓글마다 브리핑을 다시 생성하지 않습니다.

브리핑에는 생성 시각과 기준 데이터 시각을 표시합니다. 새 생성이 실패하면 오류를 명시하고, 이전 브리핑을 남길 때는 현재 결과가 아닌 이전 시점의 내용임을 표시합니다. 과거 내용을 새 분석처럼 보이게 하지 않습니다.

설명 보강 이후 주문 속도와 부정 비율의 전후 수치를 표시할 수 있으나, “안내 덕분에 매출이 올랐다”는 인과적 결론은 내리지 않습니다. 고객에게 메시지를 발송하거나 실제 방송 자막을 수정하는 기능은 포함하지 않습니다.

## 8. 데이터 흐름과 기존 프로젝트 활용

기존 [프로젝트 가이드](../../../README.md)에 기술된 React·Vite, FastAPI, Psycopg 3, HorizonDB 구성을 활용합니다. 기존 배송 데이터 모델이나 배송용 프롬프트에 홈쇼핑 필드를 억지로 추가하지 않고, 도메인을 구분해 확장합니다.

처리 흐름은 다음과 같습니다.

1. 가상 이벤트 생성기가 주문·댓글을 만들고 HorizonDB에 저장합니다.
2. 주문 집계는 LLM과 독립된 조회 경로에서 계산합니다.
3. 댓글 분석 작업은 미처리 댓글을 제한된 크기로 묶어 실제 LLM에 전달합니다.
4. 검증한 분석 결과를 원문 댓글 ID에 연결해 저장합니다.
5. 화면은 집계·분석 상태·댓글 근거를 갱신합니다.
6. 별도 브리핑 작업이 검증된 집계와 댓글 근거로 운영 요약을 생성합니다.

필요한 논리 데이터는 방송, 상품·안내 정보, 데모 실행, 주문 이벤트·주문 상태, 원문 댓글, 분석 결과, 대응 기록, 브리핑입니다. 각 데이터는 실행과 방송·상품을 식별할 수 있어야 합니다. 물리 테이블명과 API 경로는 구현 계획에서 정합니다.

기존 LLM 연결 설정을 재사용하는 것이 기본 방향입니다. 직접 모델 API와 DB 경유 provider 중 현재 설정에 맞는 경로를 사용할 수 있는지 구현 전에 확인합니다. 배송 도우미의 도구·프롬프트는 재사용 대상이 아닙니다. 이 문서 작성 중 모델 호출이나 Azure 설정 변경은 하지 않았습니다.

댓글·브리핑 분석은 서버 측에서 수행합니다. API key를 브라우저에 전달하지 않으며, 댓글 원문은 모델 지시가 아닌 분석 대상 데이터로 취급합니다.

단일 데모 실행의 상태와 결과는 DB에 보관합니다. 서버가 재시작되면 이벤트 생성을 중지 상태로 표시하고 명시적으로 재개합니다. 이미 저장한 이벤트·분석을 임의로 지우거나 재생성하지 않습니다. 복수 서버 프로세스가 있더라도 같은 실행에 생성기·분석 작업이 중복 배정되지 않도록 구현 계획에서 실행 소유권을 정합니다.

## 9. 갱신·지연·실패 상태

다음 값은 초기 수용 목표입니다. 기존 환경에서 측정하지 않았으며, 실제 모델·할당량에 따라 조정이 필요하면 구현 전에 변경 근거를 남깁니다.

| 대상 | 초기 수용 목표와 표시 |
| --- | --- |
| 주문 갱신 | 앞서 제안한 기본 이벤트 속도에서 DB 저장 후 화면 반영까지 5초 이내 |
| 댓글 분석 | 같은 속도에서 20건 이상의 댓글을 관찰해 수집부터 분석 결과 표시까지 p95 15초 이내를 목표로 측정 |
| 모델 처리 지연 | 대기 건수와 가장 오래 대기한 댓글의 경과 시간을 표시 |
| 모델 실패 | timeout·할당량·잘못된 응답 등을 구분해 표시. 원문과 실패 상태 보존 |
| 화면 연결 실패 | 연결 오류와 마지막 정상 갱신 시각 표시. 기존 값을 최신인 것처럼 표시하지 않음 |
| 브리핑 갱신 실패 | 실패 상태와 이전 브리핑의 생성 시각 표시 |

재시도 횟수와 timeout은 구현자가 기존 호출 정책을 확인해 정합니다. 무한 재시도는 금지하며, 수동 재시도가 성공해도 같은 댓글 분석이 중복 집계되면 안 됩니다. LLM 실패가 주문 집계를 차단해서는 안 됩니다.

실제 LLM의 결과를 고정된 데모 판정으로 대체하는 모드는 첫 버전에 포함하지 않습니다. 테스트에서만 명시적으로 mock provider를 사용할 수 있고, 실제 연결 검증 결과와 구분해서 보고합니다.

## 11. 승인과 구현 계획의 경계

이 문서는 요구사항과 설계 제안입니다. 현재 브라우저의 HTML 목업은 고정 장면과 가상 판정을 보여주는 논의 도구이며, 실제 서비스나 실제 LLM 처리 결과가 아닙니다.

문서 승인 후 별도 구현 계획을 작성합니다. 구현자가 정할 사항은 물리 스키마, API·URL, 화면 컴포넌트 경계, polling·streaming 선택, 작업 실행·소유권 방식, batch 크기, timeout·재시도 정책과 상세 테스트 배치입니다. 기존 도구와 배포 환경을 우선 사용하고, 새 인프라나 의존성이 필요하면 이유를 먼저 설명합니다.

기존 작업 트리의 변경은 유지합니다. 이 요구사항 작업은 서비스·인프라 파일을 수정하거나 배포하지 않습니다.
