# Commerce Micro-batch Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace per-comment classification with real multi-comment LLM requests and improve topic chips and desktop header readability.

**Architecture:** Keep raw comments and existing labels. Atomically claim at most ten unassigned comments into an immutable DB job when ten have arrived or the oldest has waited five seconds; a new HorizonDB `on_change` pipeline classifies that job in one request. Validate the returned IDs and per-comment labels before writing existing label records; preserve run/version isolation and explicit failures.

**Tech Stack:** Existing FastAPI/Pydantic/Psycopg/HorizonDB `azure_ai`, React/TypeScript/CSS; no new dependencies or cloud resources.

**Spec:** [Approved home-shopping design](../specs/2026-10-28-tv-home-shopping-design.md), amended by the user's 2026-10-28 request: micro-batch at five seconds OR ten comments, bordered topic chips, wider browser/desktop header only.

## Global Constraints

- Five seconds starts with the oldest unassigned comment, not with the last arrival.
- Ten comments triggers eligibility immediately; every batch has 1–10 comments; empty queues produce no requests.
- The five seconds bounds collection eligibility, not LLM completion or the durable scheduler's execution delay.
- Keep actual `gpt-5.4-mini` classification through a HorizonDB AI pipeline; no synthetic classifications.
- Preserve existing Fleet, orders, historic labels, simulation controls and mobile header layout.
- Do not change Azure policy, account authentication, existing endpoint or secret values.
- Keep unrelated dirty worktree changes. Use the existing native execution approach.

## Review Focus

- Continuous arrivals must not extend the oldest comment's five-second deadline: Task 1 boundary tests.
- Simultaneous ingest/flush must not assign one comment twice: Task 2 DB integration check.
- Missing, duplicate or invented result IDs must fail explicitly, never shift labels by array position: Tasks 1/2 tests.
- Retry/reset must not allow a late prior batch to overwrite current labels: Task 2 version/assignment checks.
- Desktop nonwrapping must not push the selector off-screen or change mobile layout: Task 3 browser measurements.

- Modify `backend/app/commerce/simulator.py`: deadline-aware enqueue separate from generation and briefing.

- Modify `docs/home-shopping.md`: actual batching behavior, measured batch sizes/latency and rollout status.

### Task 1: Batch contracts and deterministic boundary tests

**Interfaces**

- `batch_ready(count: int, oldest_at: datetime, now: datetime) -> bool`: true for count ≥10 or nonempty oldest age ≥5 seconds.
- `BatchMember`: comment ID, original content and source version.
- `BatchClassification`: `results` array; each entry has comment ID and fixed sentiment/intent/topic fields. Evidence is linked to the exact original input by ID, not regenerated by the model.
- `validate_batch(raw: str, members: list[BatchMember]) -> dict[str, Classification]`: exact ID-set equality, no duplicate IDs, strict enum/evidence validation.

- [ ] Write `test_tenth_comment_flushes_without_waiting` asserting 10 at age 0 are ready, and `test_empty_batch_is_never_ready`.
- [ ] Write response tests for reordered IDs, missing/duplicate/unknown IDs, mixed sentiment/intent, invalid JSON and invented evidence.
- [ ] Run `.\.venv\Scripts\python.exe -m pytest tests\test_commerce.py -q` from `backend`; first fail for absent batch contracts, then implement the contracts and repeat to PASS.

### Task 2: Durable multi-comment requests and safe rollout

**Interfaces**

- `CommerceRepository.enqueue_batches() -> int`: atomically create ready jobs for the active run; ingest also checks the count trigger.
- `reconcile()`: consume new job outputs, map by ID and write existing `commerce.labels`.
- Final pipeline name `commerce_comment_classifier_v3`, source `commerce.analysis_batches`, sink `commerce.batch_results`. v2 was the intermediate model-output format tested during this change.
- Comments gain nullable `analysis_batch_id`; batch records retain source versions. A retry clears the assignment, updates comment version and creates a new immutable job.

- [ ] Add the two job tables and the additive assignment column; no deletion/rewrite of historic comments, labels or v1 raw output.
- [ ] Claim oldest unassigned comments with transactional ownership and row locks; cap each job at ten; serialize a single JSON input containing ID/content pairs.
- [ ] Call the count-trigger check after a successful insert; check the time trigger periodically even after generation is paused.
- [ ] Use a v2 `ai.generate` instruction returning a `results` array, with sufficient bounded output tokens for ten classifications.
- [ ] Preserve the v1 pipeline while preparing v2, then retire its definition/trigger with `ai.drop_pipeline` while preserving raw data and labels. Actual testing showed a paused v1 trigger raises on INSERT; pausing alone is insufficient. Enqueue only unclassified current versions.
- [ ] Fan out validated results by ID. Reject malformed batch output explicitly for assigned comments; never silently mark absent results neutral. Match current run, assignment and source version before storing.
- [ ] Update retry to create fresh assignments and ignore delayed prior jobs; keep SQL dashboard aggregates unchanged.
- [ ] Adapt the live check: inject 20 comments and assert exactly two ten-member jobs, plus a partial batch that is absent before five seconds and present after it.
- [ ] Validate repeated flushes, idempotent enqueue and late results after retry/reset; rerun the focused commerce/API tests and existing backend suite.
- [ ] Pause the deployed simulator, drain old work, apply schema/pipeline transition and test real mini outputs. Preserve the existing endpoint and auth configuration.
